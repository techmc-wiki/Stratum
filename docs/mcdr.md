# MCDR Runtime Contract

MCDR is an Agent-supervised child runtime. Stratum starts and stops the outer
MCDR process, while MCDR starts the Minecraft server process from its generated
`config.yml` `start_command`.

MCDR is not the Stratum lifecycle owner. The Controller owns authoritative
Project, Room, Session, Operation, Checkpoint, and Artifact metadata. The Agent
owns local runtime process supervision, runtime directories, generated MCDR
configuration, logs, and stop/kill behavior.

## Current Implementation

The implemented runtime path is:

1. The Controller validates Session, Environment, RuntimeProfile, resource, and
   artifact-readiness state.
2. The Agent materializes the Environment into the Session runtime root.
3. The Agent detects Java, deploys the server jar, prepares MCDR directories,
   writes `environment-materialization.json`, writes MCDR `config.yml`, writes
   `eula.txt` and `server.properties`, and starts the MCDR RuntimeProfile.
4. MCDR reads `config.yml` and starts Minecraft with the generated Java command.
5. The Agent captures MCDR stdout/stderr, watches readiness log patterns,
   records process status, and stops MCDR through the configured stop strategy.

Key implementation files:

- `internal/agent/mcdr/supervisor.go` - MCDR start, stop, restart, command, and
  readiness coordination.
- `internal/agent/mcdr/config_writer.go` - generated MCDR `config.yml`.
- `internal/agent/process/materialization_environment.go` - Environment
  materialization and runtime metadata.
- `internal/agent/process/layout.go` - Session and MCDR runtime directories.
- `internal/agent/serverjar/` - server jar download and deployment.
- `internal/agent/java/` - Java detection and version compatibility.
- `runtime-profiles/*.json` - trusted RuntimeProfile definitions.

## Ownership Boundaries

- **Controller**: authoritative metadata, operation coordination, permissions,
  scheduling, audit, and Session state.
- **Agent**: runtime directory ownership, Java/server jar materialization, MCDR
  process lifecycle, logs, readiness, stop/kill behavior, and local manifests.
- **MCDR**: Minecraft child process startup via `config.yml`, MCDR plugin loading,
  and MCDR-level command handling.
- **Lucy**: package resolution, lock generation, mod download planning,
  installation, and integrity verification. Lucy never starts, stops, or commands
  a JVM.

The Controller must not call MCDR directly. Agents report observations back to
the Controller, but Agents must not directly mutate Controller repositories or
authoritative Session state.

## Runtime Layout

Each Session has a runtime root under the Agent `--runtime-root`:

```text
sessions/<session-id>/
  config/
    environment-materialization.json
  mods/
  world/
  logs/
  work/mcdr/
    config/
      config.yml
      permission.yml
    plugins/
    server/
      eula.txt
      server.properties
      <server-jar>
    logs/
    tmp/
```

All MCDR paths are derived from `process.SessionRuntimeLayout` and
`process.MCDRRuntimeLayout`. RuntimeProfile JSON remains trusted deployment
configuration and must stay argv-based; no user-provided shell commands are
accepted.

## MCDR config.yml

`config.yml` is generated by the Agent from materialization metadata:

- `working_directory` points at `work/mcdr/server`.
- `plugin_directories` points at `work/mcdr/plugins`.
- `config_directory` points at `work/mcdr/config`.
- `start_command` is generated from the detected Java executable and deployed
  server jar name.
- optional proxy settings come from deployment environment configuration.

The generated `start_command` is a shell command consumed by MCDR, but Stratum's
RuntimeProfile command remains argv-based. Shell argument quoting is intentionally
minimal: arguments are quoted only when they contain whitespace, so Windows shell
execution can resolve commands such as `java` correctly.

## MCDR Bridge Package

`internal/agent/mcdrbridge` remains a metadata planning package. It builds and
validates launch-plan manifests for inspection and diagnostics. It is no longer
the primary runtime path, and it must not be described as future runtime
execution.

The bridge is useful for:

- recording expected MCDR directories and command metadata,
- validating session-relative launch-plan paths,
- inspecting launch-plan manifests without mutating runtime state,
- documenting deployment expectations for diagnostics.

It does not start MCDR, install dependencies, download server jars, call Lucy, or
change Controller metadata.

## Carpet and Prime Backup Baseline

GTMC Fabric environments should become server-ready baselines before Web UI work:

- **Carpet** is a Fabric mod and belongs in the Lucy/Fabric mod materialization
  path. When `carpetRequired` is true, materialization should ensure a compatible
  Carpet jar is installed in the Session `mods/` directory and readiness should
  block Session start if Carpet is missing or fails integrity verification.
- **Prime Backup** is an MCDR plugin and belongs in the MCDR plugin
  materialization path. It should install under `work/mcdr/plugins/` with any
  required config under `work/mcdr/config/`, separate from Fabric mod handling.

This split keeps Fabric mods, MCDR plugins, and runtime process ownership clear.
Prime Backup should be treated as baseline safety infrastructure for shared
technical-testing sessions, not as a generic user artifact requirement.

## Validation

Current validation artifacts:

- `internal/agent/mcdr/e2e_real_minecraft_test.go` runs with the `integration`
  build tag and validates real MCDR startup using a downloaded Fabric server jar.
- Standard tests cover MCDR config generation, manifest handling, process
  lifecycle, command injection, restart, crash observation, and stop behavior.

Useful commands:

```bash
go test -count=1 ./internal/agent/mcdr
go test -tags=integration -count=1 -v ./internal/agent/mcdr -run TestE2ERealMCDRMinecraftBoot
```

The integration test requires Java, Python, and MCDReforged on the host. On
Windows, use an absolute Java executable path when PATH inheritance through the
MCDR child process is unreliable.
